# 0002 — 成长相册与班级相册是两个领域概念，不合并

- Status: Accepted
- Date: 2026-11-01

## Context

两端都叫「相册」，但实现与语义不同：

- 家长「成长相册」是成长记录媒体的**派生视图**：按孩子、月份、记录日期分组，没有相册实体，也不支持家长上传/编辑/分类。
- 老师「班级相册」是**独立实体**：`albums` + `album_photos`，有标题、分类、日期、1–50 张照片，只属于当前班级。

设计工件曾写「上传后家长可在成长时光里看到」，暗示班级相册应成为家长可见内容；但契约明确本期不支持家长端浏览。两者若继续同名不加区分，后续会出现「老师发的照片家长看不到」「家长相册里找不到班级活动」的预期落差。

## Decision

保留两个概念，不合并：

- **成长相册**：只读派生视图，不建相册实体；继续由成长记录媒体驱动，服务「按孩子/时间回看」。
- **班级相册**：老师策展的班级照片集，是独立实体；经发布后供本班家长浏览，服务「班级活动照片」。
- 两边共享照片文件时只引用同一 URL，不复制实体；成长记录与班级相册各自保留自己的组织维度。

## Consequences

- 契约、UI 文案与 glossary 必须明确受众，禁止再用不加限定的「相册」指代两者。
- 班级相册需要发布状态、照片-幼儿关联、家长可见接口；成长相册不需要上传/编辑能力。
- 同一张照片可能同时出现在成长记录与班级相册，需允许引用而不重复存储。
- 若未来要合并，必须先统一「相册」的实体语义，成本高；因此现在明确边界。

## Alternatives considered

- **全部合并进成长记录**：家长立刻可见，但失去班级策展、分类、统计与活动相册的组织能力。
- **让班级相册成为成长相册的上传源**：会把两套实体耦合，家长相册被迫继承班级维度的权限与发布状态。
- **两端都叫「相册」不做区分**：短期省事，长期制造用户预期落差与客服成本。
