#### ★ 「带量」的量到底是什么意思 —— 结论

**结论：`foodGram` 是「每人每餐的可食克数」，且它同时就是采购口径的克数（当前配置下不除食部）。** 三条独立证据：

1. **页面表头写明**：周食谱编辑器明细表的列头是 **「数量(一人均量：克)」**。`[页面]`
2. **采购清单页头写明并给出换算**：`计划食谱采购清单` 页头写 **「食物需购量/每人克(g)」**，页眉显示 **「计划就餐人数：251」**；单位切到「斤」时：面条 30 → 15.06；紫菜(干) 2 → 1.004。`[页面]`
   验算：`30 × 251 / 1000 = 7.53 kg = 15.06 斤`；`2 × 251 / 1000 = 0.502 kg = 1.004 斤`。**完全吻合，无食部折算、无熟制折算。**
3. **接口冗余字段自证**：`planTotal = foodGram × stuNum / 1000`（公斤）。面条 `30 × 251 / 1000 = 7.53` ✅；猪瘦肉 `10 × 251 / 1000 = 2.51` ✅；紫菜 `2 × 251 / 1000 = 0.502`（接口给 0.5，四舍五入到 1 位）✅。`[接口]`

**关于「市品重量 vs 可食重量」**（`foodInputType`）：
- 当前租户配置为 **1 = 市品重量**，且 187 行 detail 的 `isFromMarket` 全为 `1`。
- 语义推断：`市品重量` = 采购/称重口径（带不可食部分），`可食重量` = 入口口径。若配成可食重量，`foodGram` 表示可食部分克数，采购量应 = `foodGram / (eatPart/100)`。
- **该换算式未能在本次取证中直接验证**（页面无对应数据，且不能改配置）→ **`[未确认]`**。`eatPart` 字段确实随食物变化（鸡蛋 88、核桃(鲜) 43、面条 100、腰果 100），是这条换算的燃料。

**「量」的维度**：
- **无年级/班级维度**。一份食谱 = 一个集体对象 = 一组班级，全园统一用量，`foodGram` 只有一个数。`[源码]` 的年级字段（grade1..4StuNum）**只用于算人数**，不用于算克数。

- **不是周维度**：周总量由 `weekAmountStr` / `dayAmountList` 事后聚合，明细本身不存周量。`[接口]`

**生重/熟重**：系统**只处理生重（原料）**。食谱里挂的是「食物」（orgFood，来自食物库的营养成分表），不是「成品菜」的营养。菜（`orgRecipeAlias`）只是个分组标签，不参与营养计算。`[接口]` + `[页面]`（采购清单按原料列）

#### 营养是怎么存的、怎么算的

**存**：每一行 detail 冗余存一份该食物**每 100g 可食部**的营养成分值。证据：
- `新增食物` 弹窗标题下明确标注 **「(以每100g可食部计)」**。`[页面]`

- `nutriHeat = nutriEnergy × 4.186`（286 → 1197.196）。`[接口]`

**算**：服务端按 `foodGram / 100 × nutri值 × eatPart/100`（推断）聚合到人日、再除以人数得到「平均每人每日」，与 DRIs 比。`[未确认]` 具体公式在服务端，未见源码。但结果可交叉验证：

### 3.2 周食谱编辑器（网格型，核心交互）

**结构** `[页面]`：
- 表头：计划食谱名称 / 可选日期（如 `2026-10-26至2026-11-01`）/ 集体对象名称（全体幼儿）/ 食物重量输入方式（市品重量）/ 周次（9）/ **更改就餐人数**
- 顶部按钮：**更新食谱 / 清空食谱 / 保存草稿**
- 主体：**列 = 日期（7 天，周一到周日）+ 每餐次一行**。行 = 餐次（早餐/早点/午餐/午点/晚餐）
- 单元格内展开明细表，列头 **「数量(一人均量：克)」**，行 = 菜名 → 食物名 → 数量
- 行内操作：**添加菜谱 / 移除菜谱 / 添加食物 / 移除食物 / 同类替换**

**关键交互推断与实证**：

### 3.6 菜谱库：存在，且是「用出来的」，但没有管理界面

**结论：有菜谱主数据，但它不是预制库，而是园所自己在编食谱时顺手沉淀出来的私有词条；平台没有给它任何独立的管理页面。**

`[接口]` `POST /diet/recipe/getOrgRecipeListPaged.do {pageNum, pageSize, like}` → 本租户 **total = 2360 条**（对比食物库仅 1744 条）。单条结构极简：

```
{ orgRecipeID: 109969260, orgID: 43957, alias: "鲜菇鲜肉云吞",
  writeCode: "XGXRYT", addMethod: 5, status: 1 }
```

- `alias` = 菜名（唯一业务标识，见下方重名规则）
- `writeCode` = **菜名拼音首字母简写**，由 `/diet/pinyin/getPinyin.do {keyStr}` 生成，用于检索加速
- `addMethod` = 该词条是怎么进库的（5 已观测，其余枚举 `[未确认]`）

`[接口]` `POST /diet/recipe/getOrgRecipeInfo.do {orgRecipeID}` 取详情，返回两组：
- `infos[]` = 菜谱配方 `{orgRecipeInfoID, orgRecipeID, orgFoodID, alias, foodGram, status}`
- `foods[]` = 上述每个 `orgFoodID` 的完整营养记录（27 项营养 + `typeStringOne/Two/Three`）

也就是说**菜谱 = 一组「食物 + 一人均量克数」的命名快照**，与 `dietInfo` 行同构，只是没有日期/餐次/人数。举例 `鲜菇鲜肉云吞` = 小麦粉 10g + 香菇(鲜) 5g + 猪瘦肉 5g。

#### 【添加菜谱】到底是自由输入还是选择器？——两者都是：**可自由输入的联想框**

`[源码]` `diet/js/dietAddElement.js` 生成的菜名输入框：

`onclick` 和 **每按一个键的 `onkeyup`** 都触发 `intMenuList(this)`（`diet/js/dietDropDown.js`，源码注释 `// 菜谱输入框点击`）：

```js

```

- `like` 直接取输入框当前文本 → **边打字边模糊搜菜谱库**

**输入一个库里没有的新名字 = 新建一个菜**（不会被拦），所以菜谱库是靠使用自然膨胀的。

#### 保存菜谱（把当前菜写回词条库）

`[源码]` 菜容器上有 `<button id="saveThisMenu" onclick="saveThisMenu(this)" style="background-color:#5bc0de;">保存菜谱</button>`：

1. 校验 `菜谱名称不能为空!`、菜下所有食物克数不能为空 → 否则 `judgeThisMenu` 不执行
2. `judgeThisMenu(obj, alias, details)` 查重，重名弹确认：
   `当前菜谱名称已存在，是否替换原菜谱？` — 两个按钮 **`否，仅限本次使用`** / **`替换`**
3. 后续按分支走：
   - **不重名** → `POST /diet/pinyin/getPinyin.do {keyStr}` 取简写码 → `POST /diet/recipe/addRecipe.do {alias, writeCode, infos}`，提示 `保存本次成功！`

   - **选「否，仅限本次使用」** → **不写库、不调 getPinyin**，直接把这份配方留在当前这一周的食谱里

**推论（已由数据佐证）**：菜谱库的**唯一真相是「名字」**。同名即视为同一条词条，保存时是「替换」而非「另存」；不同名则新增。所以库容（2360）远大于实际在用菜名（8 周仅 194 个不同菜名）——是历史增量累积的结果。

### 3.7 历史食谱的菜名从哪来：同名的重复率与「同名不同料」

`[接口]` 取最近 8 周完整明细（`/diet/queryDiet.do`）统计：

| 周次 | 明细行 | 不同菜名 | createMethod |
|---|---|---|---|
| 第九周 | 187 | 64 | 2 |
| 第八周 | 195 | 70 | **7** |
| 第七周 | 185 | 67 | **7** |
| 第六周 | 116 | 44 | 2 |
| 第五周 | 109 | 40 | 2 |
| 第四周 | 147 | 55 | 2 |
| 第三周 | 221 | 74 | 2 |
| 第二周 | 186 | 68 | **7** |

- 8 周共 **194 个不同菜名**，其中 **102 个在 ≥2 周出现（52.6%）**
- 高频复用：`混合坚果`×8、`葵花籽油`×8、`香米饭`×8、`苹果`×8、`火龙果`×8、`牛奶`×7、`三鲜汤`×7
- **但同名 ≠ 同模板**：102 个复用菜名里 **36 个（35%）在不同周的食物集合或克数不同**

   ```
   肉酱意大利面  猪瘦肉:10  →  猪瘦肉:15        （同一菜名，肉量变了）
   紫菜蛋花汤    鸡蛋:10    →  鸡蛋:5           （同一菜名，蛋量减半）

   牛奶          全脂牛奶粉:40 / 鲜牛奶:40      （主食来源整个换掉）
   ```

→ **结论：菜名是人工复用（打字联想 + 复制历史），但不是强约束模板。** 系统不校验「同名必须同料」，同名只是检索键。

**顺带发现一个数据质量问题**：编辑器允许在同一道菜里重复添加同一种食物而不合并数量。例如 `混合坚果` 出现 `核桃(鲜):5` 重复 5 行、`腰果:5` 重复 5 行；`牛奶` 出现 `鲜牛奶:40` 三行；`土豆烧牛腩` 出现 `牛肉(...):20` 两行。这在营养合计上是等价的（相加即可），但让「一人均量」的读数变得难读，且采购清单会合并，明细不会。

### 3.9 营养评价「合格 / 低 / 高」的判定阈值（实证）

前端**不含任何阈值常量**（全量检索 `偏低/偏高/合格/不合格/threshold/0.9/1.1/90%/110%` 在 `recipeWithAmoutAnalysis.jsp` 中均无命中），判定完全在服务端。但可以从 `POST /diet/queryIntake.do {dietID}` 的 `nutrition[]` 反推——每个营养素都成对返回百分比与结论：

```json
{ "nutritionID": 1, "nutritionName": "能量", "labels": "energy",
  "intake": 1274.66, "fullRecom": 1484.26, "recomIntake": 1410.05,
  "percents": 90.4, "unit": "千卡", "comment": "合格" }
```

**对 66 条周食谱记录（跨多个学年）× 11 项 = 726 个观测点做区间统计，边界极其干净：**

| 结论 | 样本数 | `percents` 区间 |
|---|---|---|
| `低` | 93 | 27.34 – **79.98** |
| `合格` | 505 | **80.00 – 120.00** |
| `高` | 128 | **120.07** – 211.23 |

→ **阈值就是 ±20%：`< 80%` 判「低」，`80%–120%`（含端点）判「合格」，`> 120%` 判「高」。** 对称，不存在先前提到的「非对称阈值」。钙 32.9% 被标低、铁 124.82% 被标「高」而非「异常」，都只是这一条规则的两端。

两端都出现了恰好等于 `80.00` / `120.00` 的样本且被判「合格」，而 `79.98` 判「低」、`120.07` 判「高」，所以端点是**闭区间**。

**另一个被顺带解出的系数**：`percents = intake / recomIntake`，而 `recomIntake = fullRecom × 0.95`（能量 1484.26→1410.05、蛋白质 50.7→48.17 两例精确吻合）。也就是说**报告里的「比较%」比的不是全日常量 DRIs，而是打了 95 折的「在园供给参考值」**——这与「日托园只承担一天约 95% 的营养供给」的业务含义一致，但 0.95 是否恒定、按什么配置取值 `[未确认]`（服务端）。

> 附：定性分析结论里的建议语料（「钙摄入量偏低。建议补充一些牛奶与奶制品鱼类…」）是**按营养素硬编码的固定文案**，只要该营养素判「低」就整句输出，与缺口大小无关。

## 5. 对「最小可复制范围」的判断

按「能跑通一次真实的带量食谱闭环」来划线，**必须有的**：

1. **食物库 + 营养成分字典**（含每 100g 可食部 27 项营养、食部、两级分类）—— 这是整个模块的地基，没有它营养分析无从谈起
2. **集体对象**（就餐班级集合 + 餐次位掩码 + 分配比 + 重量口径）—— 决定「算给谁、算什么口径」
3. **周食谱明细**（日期 × 餐次 × 菜 × 食物 × 每人克数）—— 唯一真正录入的数据
4. **就餐人数**（按日 × 年级）
5. **三个派生视图**：采购清单（量 × 人数）、营养分析表（量 × 营养浓度 ÷ 人数 vs DRIs）、膳食构成表

**可以后置的**：餐后调查、膳食会议、月伙食计划表（湖南定制）、草稿箱、打印/导出。

**最容易低估的两点**：
- DRIs 标准**不是一组写死的常数**：对外只见折算后的 `fullRecom` 一行，且其中脂肪/碳水可由能量与蛋白代数推出（§3.11）。把它当静态表复制会算错。另外 **0.95 这个折算系数同时出现在分子侧和分母侧**，是最容易抄漏的一处。
- 餐次是**位掩码**不是枚举序号，任何「第 N 餐」的假设都会在和原系统对接时出错。
- **导出 Excel 不是「补全版」**：它的 5 个 sheet 与页面一一对应，同样只含 10 类膳食构成、同样把「视黄醇当量」渲染成维生素A（§3.13）。照着导出文件反推口径会把上游的截断和假列一起抄进来。
