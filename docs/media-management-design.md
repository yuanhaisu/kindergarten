# 素材管理设计基线

> 状态：**现行基线**（2026-10-12 定）。任何引入「文件上传 / 附件」的业务，都应先读本文档，按「业务接入范式」接入。
> 行为需求与验收标准的规格化表达见 `openspec/specs/media-assets/spec.md`；本文档承载架构与接入指引，规格承载可验证的行为约束。

## 1. 三层模型

素材在系统中的生命周期分三层，**每层各有一个所有权中心**，任何字段的归属先回答「它属于哪一层的语义」：

```
┌─────────────────────────────────────────────────────────────┐
│ L1 文件层  files（素材本体，跨业务共享）                       │
│    物理属性：file_url / thumb_url / file_type / file_size /  │
│              duration                                        │
│    固有元数据：caption（这是什么）/ tags（标签）/ category     │
│                                                              │
│    ── 一组文件一旦上传，其身份终身不变 ──                      │
├─────────────────────────────────────────────────────────────┤
│ L2 引用层  每个业务自己的引用表                                │
│    （growth_media / notice_attachments / health_check_media…）│
│    一切「这次使用」的语义：                                    │
│      file_id（指向 L1）     ref_desc（为什么用 / 用在哪）      │
│      sort_num（本次使用的排序）  业务外键（log_id / notice_id…）│
│      ＋ 业务特有的属性（如晨检的 category=部位）               │
├─────────────────────────────────────────────────────────────┤
│ L3 展示层  素材库视图 / 各业务 UI                              │
└─────────────────────────────────────────────────────────────┘
```

### 描述的双层归属（最重要的规则）

```
      同一张向日葵照片
  L1: caption = "向日葵生长过程照片，拍摄于植物园"     ← 固有：这是什么
   ├─ L2 课件A·第3页: ref_desc = "本页插图，讲光合作用"  ← 使用：为什么用
   ├─ L2 课件B·第7页: ref_desc = "复习环节，辨认花朵"    ← 同一文件，描述不同
   └─ L2 成长记录:   ref_desc = "小明的写生作品"        ← 跨业务引用
```

**规则**：描述素材本身是什么 → L1；描述这次为什么用它 → L2。两者独立存在、各自生命周期。单层模型在多场景复用（课件系统）下必然崩坏。

### 为什么是「每业务一张引用表」而非一张多态大表

| | 多态大表（`owner_type`+`owner_id`） | **每业务一张引用表（现行）** |
|---|---|---|
| 加新业务 | 不改表 | 加一张表 |
| 引用层字段 | 所有业务字段挤一张表 | 各业务自有字段，干净 |
| 查询索引 | 多态列索引差 | 外键精确索引 |
| 权限/可见性 | 混在一处易错 | 各业务独立 |
| 跨业务聚合 | 天然支持 | 靠「统一引用表契约」聚合视图 |

引用层语义天然按业务分化（成长记录有 `log_id`，课件有 `course_id`+`page_id`，晨检有部位分类），大表会退化成互不相关的可空列集合。

**统一引用表契约**（所有业务引用表 MUST 共享的字段命名）：
`file_id` / `ref_desc` / `sort_num` / 指向业务实体的外键。后台的「素材被引用情况」视图按此契约 JOIN。

## 2. 标签体系

标签是素材库的检索面。幼儿园场景的三个放大因素：内容高度同质（「户外活动」每周都拍）、使用者非专业（不会写规范文件名）、复用需求明确（课件/报告/宣传都要挑素材）。

**现行规则**：标签按 `sys_dict` 字典驱动，与现有字典体系同源。

| 维度 | 载体 | 驱动 |
|---|---|---|
| 素材分类（如 活动/课程/餐饮/环境） | L1 `files.category` | 系统字典 |
| 素材标签（如 户外/手工/自然/节日） | L1 `files.tags` | 受控标签集——园所可在字典中增删 |
| 使用上下文 | L2 `ref_desc` | 自由文本 |

- 纯自由标签在幼儿园会被用成「春天/春季/春/春日」的一团乱麻，**默认受控**；园所通过字典自配扩展
- 标签挂 L1 不挂 L2——「这是户外素材」是素材固有属性；L2 的业务分类（如晨检部位）是业务语义，与素材标签是两回事

## 3. 版本与替换

| 场景 | 语义 | 规则 |
|---|---|---|
| 编辑记录换图 | **解绑** | 移除引用 → 解除绑定；文件本体不动 |
| 素材更新（重传同名更新版、证书续期） | **原地替换** | `uploader` 上传新文件 → **新 `files` 行** → 引用更到新 `file_id`；旧行成孤儿（见 §4） |
| 头像/logo 换代 | 原地替换 | 同上 |

**现行规则：不做 `version` / `replaces_id` 字段**。理由：替换的实质是「引用转向新文件」，旧引用不影响历史记录（历史记录有其 `ref_desc` 与快照语义）；引入版本链是素材库增强能力（「素材历史版本」）的范畴，等该功能立项时再评估，届时旧行可作为版本历史的数据基础。

## 4. 删除与孤儿治理

**绑定与删除是两件事**：

| 动作 | 谁做 | 效果 |
|---|---|---|
| 解除绑定 | 业务编辑（如老师移除照片） | `log_id` 置空，文件行保留 |
| 删除文件行 | 管理侧操作 | **仅允许删除无任何引用的文件**；有引用时须先解绑 |
| 物理删除 OSS 对象 | 定时任务 / 运维 | **不做即时物理删除** |

**现行规则**：
- 删除文件行是**软删**（`deleted_at`），保持可恢复
- OSS 对象不即时物理删除——物理清理由孤儿清理任务承担（扫描 `deleted_at` 超期 或 无引用超期的行）
- **孤儿**（`files` 行存在但无引用）允许存在——上传即弃的残留不影响任何展示（无引用即无可见性）；清理机制本身**待素材库功能启动时实现**，当前以「可识别（无引用）可清理（软删）」为标准

## 5. 可见性

**一票规则：可见性永远由 L2 业务引用决定。L1 文件层不承载任何可见性概念。**

- 同一文件被两条业务引用（一条班级可见、一条仅家长本人）时，两条引用各自按所属业务的可见性规则生效——文件层若加「私有/公开」标记，会在跨业务引用时自相矛盾
- 素材 URL 的获取必须先经过业务层的可见性校验；**上传接口返回的对象地址不得被当作「可分享地址」直接外发**
- 新建业务引用表时 MUST 评审：该业务的可见性规则是什么（谁能看到这些引用）

## 6. 业务接入范式

新业务接入素材时只做三件事，**不做**：新上传端点、后端 OSS 依赖、客户端自拼 URL：

```
① L2：业务表加引用字段（file_id / ref_desc / sort_num ＋ 业务外键）
② 前端：复用 http.js 的 uploadFile 封装（三端同构）上传，拿 file_id
③ 后端：保存时按 file_id 校验（存在、未被其他记录占用）并落库引用行
```

上传端点统一为 `POST /common/upload`（multipart，`biz_type` 标记业务），OSS 依赖只存在于 `FileService` 一处。
