## 8.1 权限模型概述

平台采用 **双层权限模型**：

| 层级 | 适用端 | 机制 | 实现 |
|------|--------|------|------|
| **接口鉴权** | 后端所有 authed 接口 | Casbin RBAC | `CasbinRBAC` 中间件检查 `(role, path, method)` 三元组 |
| **前端鉴权** | 管理后台 | 权限码检查 | Pinia `permission` store + 路由 `meta.permission` + 菜单过滤 |

小程序端（老师/家长）不使用 Casbin 权限码，而是通过 JWT 中的 `role` 字段在路由层面分区：`/teacher/*` 只接受 `role=teacher` 的 token，`/parent/*` 只接受 `role=parent` 的 token。

## 8.3 接口层 Casbin 鉴权

### Casbin 模型定义 (`configs/rbac_model.conf`)

```
[request_definition]
r = sub, obj, act   # sub=角色, obj=路由路径, act=HTTP方法

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _            # 用户 → 角色 的继承关系

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && keyMatch2(r.obj, p.obj) && r.act == p.act
```

### 中间件执行逻辑

`CasbinRBAC` 中间件：
1. 从 JWT 提取用户的所有角色（UserRole 表中的 role 字段）
2. 遍历每个角色，调用 `enforcer.Enforce(role, path, method)`
3. 只要任一角色匹配允许策略 → 放行；全不匹配 → 403

### 策略示例 (`configs/rbac_policy.csv`)

```csv
p, super_admin, /api/v1/admin/*, *
p, admin, /api/v1/admin/dashboard/*, GET
p, admin, /api/v1/admin/students/*, *
...
```

## 8.4 前端权限控制

### 管理后台 (`admin/`)

**三层控制**:
1. **路由守卫** (`middleware/permission.ts`): 检查 `route.meta.permission`，无权限则重定向 403
2. **菜单过滤** (`constants/menus.ts` → `Sidebar.vue`): 只渲染用户拥有的权限码对应的菜单项
3. **页面内按钮**: 通过 `stores/permission.ts` 的 `hasPermission()` 方法控制操作按钮显隐

**超级管理员模式**: `permissionCodes = ['*']` 时跳过所有权限检查。

### 小程序端

小程序的权限控制仅依赖于登录时选择的角色（`role=teacher` 或 `role=parent`），由后端路由前缀 `/teacher/*` 和 `/parent/*` 进行隔离。小程序前端无需额外的权限码管理。

## 8.5 多园所场景下的权限

对于跨园所用户（如同一人是 A 园老师和 B 园家长），`UserRole` 表为每个 `(user_id, kindergarten_id, role)` 组合创建独立记录。API 请求中的园所上下文由后端自动解析，确保：

- 老师在 A 园的角色不会泄露 B 园的数据
- 家长在 A 园的子女信息不会出现在 B 园的接口响应中
- 管理员只能管理其所属园所的数据
