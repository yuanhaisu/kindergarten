# Proposal

## Why

接送管理（pickup）的托管凭证链在实现上是断的：授权人比对从未写入（`isAuthorized`/`PickupPersonID` 声明后从未赋值，注释「检查是否为授权接送人」是空壳）、扫码登记链路三段对不上（前端只传 `qr_code`，service 第一步就因 `StudentID==0` 拦死，而 QR token 里明明内嵌了 studentID）、滞留儿童无任何告警。结果是「谁能接走孩子」这条安全主线目前只是数据收集，不是准入控制。

对五条托管硬属性（授权闭合 I1 / 托管完整 I2 / 事件完整 I3 / 不可抵赖 I4 / 时效闭环 I5）逐条核对，**五条全部违反**。本次用「今日接走人指定 + 码绑人」把 I1/I4 补上，用人工滞留处置把 I5 从「完全不管」提升到「可控可见」。

## What Changes

### 1. 今日接走人指定（家长端）

家长在授权人列表里指定「今天谁来接走」，二维码随之绑定到**具体的人**。

- 码结构自包含：`code` + `student_id` + `authorization_id` + `expire_at`，后端从码解出全部信息
- token **不再内嵌 studentID**（现状 `PKUP_{studentID}_{yyyyMMdd}_{hex}` 泄露学生 ID，可枚举）
- 码生成时双重校验：被指定人必须在授权集合内且 `review_status=1` 且 `status=1` 且未过期
- 码仍「当日过期 + 一次一焚」（不变）

### 2. 接走登记真正受授权约束（老师端）

**扫码路径**：前端只传 `qr_code`，后端按码查出 `student` + `authorization`，再次校验授权仍有效，落 `PickupPersonID`，码置失效。返回孩子与接走人的姓名/照片供老师**人证对照**。

**手动登记 = 例外通道**（产品决策 2026-10-07）：

- 老师从授权人列表选人 → `PickupPersonID = auth.id`，`manual_override = false`
- 或标「非授权/临时」+ 填名字 → `PickupPersonID = NULL`，`manual_override = true`（记录 override 原因）
- 例外通道使 I1 闭合到「例外被显式记录、可观测」层级，不阻断紧急情况

### 3. 送入（dropoff）维持现状（产品决策 2026-10-07，与设计稿有分歧）

送入**不走码、不记交接人、不要理由**，只作为「孩子到了」的到场标记。**这是对 `design-data/admin-05-接送记录页.json` 的有意偏离**（该设计稿示例含「入园 / 妈妈（李丽）」，即入园也记接送人）——分歧见「与设计稿的分歧」一节。

### 4. 托管序列最小改法（B1）

现状防重规则 `WHERE date = ? AND type = ?` 使同日多次往返无法登记。改为**不允许连续同类型**：

```
送入 → 接走 → 送入 → 接走   ✓
接走 → 接走                 ✗
送入 → 送入                 ✗
```

派生状态语义相应改为**看最后一条**：「已入园」= 最后一条是送入，「已接走」= 最后一条是接走（而非「今天有过送入/接走」）。

**理由必填规则**：

| 情形 | 理由（Remark） |
|---|---|
| 首次接走、窗口内 | 可选 |
| **重复接走**（当日第 2+ 次） | **必填** |
| **提前接走**（早于班级放学时刻） | **必填** |
| 重复送入 | 不要理由 |
| 是否异常 | 老师**手动标记**，不自动置 `IsAbnormal` |

**提前接走判定**：班级可配放学时刻（默认 **16:00**，产品决策 2026-10-07）。早于该时刻的接走要求理由；迟接不在此规则内，归入滞留处置。**默认值与设计稿隐含阈值不一致**（见分歧清单）。

### 5. 滞留人工处置 + 超时未接计数

- 老师端 / 管理端「未接走」名单在放学时段**高亮**
- **一键通知家长**：写入 `Message`（`MessageTypePickup`），打通「接送事件 → Message」最小发送路径
- **超时未接计数**进统计（口径：截止时刻后仍在园且未接走的学生数）
- 顺带救活 `NotifyOnPickup` 死配置：孩子被接走时按该配置推送（同一条发送路径，换个触发点）
- **不建调度器**：滞留发现依赖老师打开页面（产品决策 2026-10-07，避免为本轮新建定时基础设施）

### 6. 契约同步

**本次将修改 `backend/api/`，属于契约变更。** 同时修补既有契约漂移：

- `GET /admin/pickup/authorized-persons` 已在 router 与前端存在，但漏写进 `api-admin/08-pickup.md`
- `PUT /teacher/pickup/authorized-persons/:id/approve|reject` 已注册，但前端未调用、文档未写
- 家长端响应字段名与文档不一致（文档 `qr_image_url`/`id_card_tail`/`status_label` vs 实现 `qr_code`/脱敏 phone/`review_status_label`）
- 老师端 `GET /records/:id` 文档是扁平对象，实现返回 `{"record": {...}}` 包装

## Capabilities

### New Capabilities

- `pickup-custody`: 幼儿托管转移的证据链与准入控制——接走人授权绑定、接送凭证（二维码）生成与核验、接送登记留痕与例外通道、托管序列与理由必填、滞留可见与家长通知。送入（dropoff）不在本能力的证据要求内。

### Modified Capabilities

（无。现有 specs 仅 `achievement-award` 与 `growth-feed`，与接送无重叠。）

## Impact

**涉及端**：`teacher/`（老师端）、`parent/`（家长端）、`admin/`（管理端）**三端全改**。

**触点面**（详见 `design.md` 跨端触点清单）：

- Go `domain` / `repository` / `service` / `handler`
- `router.go` 路由与 `rbac_policy.csv`
- `backend/api/` 三端契约（**契约变更**）
- 老师端 `pages/pickup/*`、家长端 `pages/pickup/*`、管理端 `pages/pickup/`
- design token（若涉新增视觉元素）

**契约变更字段溯源**（规则要求逐字段指认，指认不出的不写进契约）：

| 字段/端点 | 溯源 |
|---|---|
| 扫码响应 / 二维码响应新增 `person:{name,photo}` | 业务场景：A2「码上带名字」人证对照（产品决策 2026-10-07）。⚠️ `design-data/` **无**家长端接送/二维码设计稿，属设计缺口，建议补 |
| 扫码响应新增 `student:{name,photo}` | 同上；现有实现已有 `student` 对象，仅补 `photo` |
| 接走登记请求新增 `authorization_id` / `manual_override` / override 原因 | 业务场景：I1 授权闭合 + 例外通道（产品决策 2026-10-07） |
| 接走登记请求 `remark` 约束收紧（重复接走/提前接走必填） | 业务场景：留痕举证（产品决策 2026-10-07）。字段已存在，仅改校验 |
| 新增班级放学时刻配置 | 业务场景：提前接走判定（产品决策 2026-10-07：班级可配、默认 16:00）。⚠️ `design-data/` 无出处 |
| 滞留名单 / 超时未接计数 / 一键通知端点 | 设计稿 `admin-05-接送记录页.json` 有「本月超时未接 3」统计卡与「超时接走」类型；业务场景：档 B 人工处置 |
| `NotifyOnPickup` 从死配置转为真实消费者 | 字段已存在（`domain/pickup.go`），业务场景：孩子被接走通知家长 |
| 契约漂移修补（admin 列表端点、老师审核端点、家长响应字段名、records/:id 包装） | 业务场景：契约与实现一致（缺陷修复，非新增能力） |

## 与设计稿的分歧（显式记录，不静默吞掉）

| # | 设计稿 | 本次决策 | 处置 |
|---|---|---|---|
| 1 | `admin-05` 示例含「入园 / 妈妈（李丽）」→ 入园也记接送人 | **送入不记交接人** | 有意偏离。理由：风险不对称（接走=孩子跟人走是安全要害，送入=孩子到达风险低）。若后续要对齐设计稿，只需放开送入侧的记人，不阻塞本次 |
| 2 | `admin-5` 有「接送人」与「核验人」两列（两人） | **不建双人流程**，`OperatorID` 语义明确为核验人，契约列名用「核验人」 | 有意偏离。理由：双人交接属流程改造，本轮不扩。字段语义先对齐，流程后议 |
| 3 | 示例阈值落在 17:30(正常)–18:25(超时) 之间，约 18:00 | **默认 16:00、班级可配** | 有意偏离。设计示例是 mock 数据；阈值属产品决策，已定 16:00 |
| 4 | 「非授权接送尝试 2次」是统计指标 | **后置** | 需新建拒绝交接事件类型，本轮范围外。留待下轮 |

## 明确不做什么（Out of Scope）

| 项 | 为何不做 |
|---|---|
| **B2 请假接入**（`LeaveRequest` 与接送/出勤视图联动） | 与证据链无关，独立收益；本轮不碰请假模块可显著缩窄触点面 |
| **E1 两张表补 `kindergarten_id`**（`pickup_authorizations` / `pickup_qr_codes`） | 纯数据迁移（加列 + 回填 + 校验），`AutoMigrate` 只增不改需手写 SQL；与本轮行为变更正交 |
| **双人核验流程**（D3） | 流程改造，本轮只做字段语义对齐 |
| **拒绝/非授权接送尝试事件**（A3） | 需新建事件类型与统计口径，范围膨胀 |
| **委托链 / 转委托**（C1） | 产品决策 2026-10-07：不做 |
| **迟接（超时接走）作为独立接送类型** | 本轮只做「超时未接」计数与滞留处置；迟接落库仍是普通接走记录 |
| **调度器 / 定时核对**（I5 全自动） | 项目当前无任何定时基础设施（`cmd/api/main.go` 是纯 gin HTTP server）；本轮用人工触发替代，待真实使用验证频率后再议 |
| **身份核验二要素**（短信/人脸） | 产品决策 2026-10-07：采用「码上带名字 + 人证对照」，不做短信/人脸 |
| **二维码 HMAC 签名** | 本轮改绑人 + 一次一焚已显著提升安全性；签名属后续加固 |
| **并发/竞态控制** | 一次一焚已提供基本保护；竞态语义留待后续 |
