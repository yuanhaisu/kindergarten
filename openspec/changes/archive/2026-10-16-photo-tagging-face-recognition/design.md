# Design

## Context

动机见 proposal.md。影响设计的关键现状与规划期结论：

1. **表已存在但零写入**：`growth_media_students`（`media_id`/`student_id`/`is_auto`，联合唯一索引）自建库起从未被写入——本变更是它的首个写入方。增加 `status`/`confidence` 两列即可承载「建议/确认/拒绝」语义。
2. **选型已翻盘一次**：原定阿里云 facebody **已退市**（公告 118619：2026-10-11 停止新开通 → 2028-04-30 停服），改用**腾讯云 IAI 人脸识别**（`iai.tencentcloudapi.com`，v20200303）。其为长期产品、每月 1 万次免费额度、URL/Base64 双输入、`SearchFacesReturnsByGroup` 支持按库搜索。
3. **密钥边界**（硬规则）：腾讯云 `SecretId`/`SecretKey`、TC3 签名、所有第三方调用**只存在于后端**。小程序端没有任何第三方 SDK 与凭证——客户端只做「上传照片」与「查看结果」。
4. **图片输入用 Base64**：腾讯云支持 Base64（≤5MB）；后端从 OSS 取图 → base64 → 调 API。绕开「识别服务能否访问我方 URL」的跨云可达性问题（这也是腾讯云相对退市方案的优势被我们用上的点）。
5. **技术栈为纯 Go 单二进制**（`cmd/api` + Wire + GORM + Redis，无 cgo、无容器的既定形态）：队列/限流实现必须服从这个形态，不引入外部消息中间件。
6. **SaaS 峰值形态**：多园所节奏重叠（户外课后、午睡前批量发布），峰值可达数十 QPS 量级；识别的**非实时性**允许用队列吸收峰值。

## Goals / Non-Goals

**Goals:**

- 照片与孩子的关联可人工点名（批量 + 单张微调），家长端按「只看我的孩子」呈现
- 学生人脸底库可注册、状态可见、按园隔离；识别密钥不出后端
- 识别异步化：发布零等待、限流保配额、租户公平、预算护栏、故障降级
- AI 建议须老师确认才对家长生效（信任模型：AI 建议、老师背书）

**Non-Goals:**

- 家长端人脸授权流程（合规前置，**独立变更**；见 Risks 中的上线门槛）
- 识别结果自动确认（跳过老师）
- 本地特征值存储（云端底库为准，我方只存映射）
- 其他模块（接送、晨检）的人脸能力
- 实时识别（一律走队列）

## Decisions

### D1：供应商抽象为 `FaceProvider`，腾讯云为唯一真实实现

```go
// internal/ai/face/face.go（新包，组织方式仿 internal/storage/oss）
type Provider interface {
    // 底库：确保该学生在云端有可检索条目（幂等）
    EnsurePerson(ctx, kgID, studentID uint64, images []string) (personRef string, err error)
    // 识别：对一张图做 1:N 搜索（限定该园底库）
    Search(ctx, kgID uint64, image []byte) ([]Match, error)
    // 注销：学生转出/删除时清理云端条目
    RemovePerson(ctx, kgID, studentID uint64) error
    Name() string // "tencent" | "mock"
}
type Match struct { StudentID uint64; Score float64 } // Score 0-100（腾讯云口径）
```

- `tencent` 实现：`CreateGroup/GetGroupList`（`GroupId = kg_{kindergarten_id}`，多租户隔离落在云侧分组）、`CreatePerson/CreateFace`（底库）、`SearchFacesReturnsByGroup`（识别）、`DeletePerson`（注销）
- `mock` 实现：按可配置规则（文件名/固定映射）返回假匹配——**让无凭证环境（开发机、CI）完整跑通队列/确认/筛选全链路**，这是 mock 存在的唯一理由
- **替代方案**（未采纳）：直接在各调用点内联腾讯云 SDK。抽象让我们能用 mock 测全链路、未来换供应商（这次 facebody 退市就是教训）只改一个实现

### D2：识别任务表驱动（DB 轮询），不合入 Redis 队列

**决定**：新表 `recognition_jobs`（`media_id` 唯一 / `kindergarten_id` / `status` / `retries` / `last_error` / `next_run_at`）。worker 池按固定间隔（如 2s）批量认领 `next_run_at <= now AND status = pending` 的任务。

**为何不用 Redis 队列**：项目已有 Redis（缓存/会话），但把任务放进 Redis 会引入「任务与业务数据分离、丢任务无痕」的问题；DB 表让任务**与媒体数据同生命周期、可审计、可人工干预**（重试/跳过/排查）。单二进制形态下 2s 轮询对千级/日任务量完全够用。
**替代方案**（未采纳）：goroutine + channel 内存队列——进程重启丢任务；专业 MQ——违反「不引入外部组件」的现状。

### D3：限流用 `golang.org/x/time/rate` 令牌桶，速率配置驱动

- 全局单一 bucket（`rate.NewLimiter(qps, burst)`），所有 worker 共享——保护腾讯云配额
- `[face].qps` 配置（起步 10，峰值季在腾讯云侧买更高 QPS 包即可，**代码不改**）
- **替代方案**（未采纳）：Redis 分布式限流——单实例部署下是过度设计；将来横向扩容时再升级（接口留好）

### D4：租户公平用「按园所分组的加权认领」

认领任务时按 `kindergarten_id` 轮转（每轮每园取一个任务）——防单园大积压饿死小园。实现为认领 SQL 的 `GROUP BY kg 取每组最早一条` 的变体或应用层轮询。
**取舍**：牺牲一点吞吐（认领查询稍复杂）换取 SaaS 公平性——这是产品要求，不是优化项。

### D5：预算护栏 = 日调用计数器（Redis），触顶暂停不丢任务

- 每发起一次识别调用前 `INCR` 当日计数（Redis，按园所+全局两维）
- 超 `[face].daily_budget` → worker 停止认领新任务（已有任务保持 pending），同时记一条告警日志
- 次日自动恢复（key 带日期）；**不丢任务**——恢复后继续消费

### D6：确认流的状态机（`growth_media_students.status`）

> 设计前提：**人脸识别能力满足业务要求**（跨图召回可靠）。2026-10-15 的初测样本
> 不足以证伪或证实这一点（样本小、无标注、仅证件照缩略图）——按能力达标前提推进。
> 初测观察到分数重叠的线索记于 `docs/face-quality-report.md`，**待真实场景标注数据
> 充分后再决定是否调整阈值或交互**；若届时证实重叠，阈值配置化使得调整不改代码。

```
             识别回调（异步）               老师确认
  创建为空 ────────────────→ status=0 ───────────────→ status=1
     │                        （建议）                    （生效）
     │ 老师手动点名                                    
     └──────────────────────→ status=1（source 手工）     
                              status=2（拒绝，不再提示）
```

- **家长端只认 `status=1`**（D7）；`status=0` 的建议不进入任何家长可见链路——这是信任模型的落点
- 人工点名（`is_auto=false`）直接 `status=1`；AI（`is_auto=true`）落 `status=0` 并带 `confidence`
- 腾讯云 `Score`（0-100）→ **建议分级**：**高置信（预勾）≥ `suggest_high`（默认 80）/ 低置信（提示不预勾）≥ `suggest_low`（默认 70）/ 低于 `suggest_low` 不落建议**。阈值为配置项，真实数据校准后调整不改代码
- **老师确认仍是生效前提**（信任模型）：预勾只是「默认选中」，老师可取消/追加任何一项；未确认的建议永不对家长生效

### D7：家长端筛选在前端做，后端一次给全

- 详情响应的每个 media 项带 `student_ids`（**仅 `status=1` 的确认项**；个体记录同样给，供照片标识）
- 家长端默认视图 = `media.filter(m => m.student_ids.includes(当前孩子))`；「看全部」= 原数组
- **为何不做后端 `?only_mine=1`**：20 张量级一次拿全、切换零延迟、后端不引入查询参数与缓存问题；将来照片数上量再评估
- **个体记录特例**：不做筛选（照片本就属于这些孩子），仅显示标识——避免「筛选后把照片藏了」的荒谬

### D8：编辑态点名随媒体全量替换走同一提交链路

`media[]` 元素扩展为 `{ id?, file_id, ref_desc, student_ids?: []uint64 }`——点名与媒体在**同一事务**里重建（先删后插），沿用 `writeGrowthLogStudents` 的 upsert 模式；白名单校验（D9）。**不做独立的点名端点**——避免「媒体与点名两次提交不一致」的状态。

**AI 建议的确认**是唯一例外：建议在发布后异步到达，老师此时不在编辑页——需要一个**轻量的建议确认端点**（对 `media_student` 行做 `status: 0→1 / 0→2` 的状态迁移）。

### D9：点名对象白名单 = 本记录涉及学生

全班记录 → 本班在读学生；个体记录 → 该记录关联学生。与 `student_ids` 的目标学生校验共用同一检查函数。

### D10：建议采纳的省力路径（2026-10-15 对抗性审查后补）

**审查发现**：D6 的「预勾」只落在编辑页单张面板，而老师的主路径是「发布后回详情页看建议」——在那里每条建议都是【确认】【拒绝】两个按钮，22 条建议 = 22 次点击；且列表无任何入口提示有待办建议，建议会静默烂掉。

**决定**：
1. **一键确认高置信**（`POST /teacher/growth/logs/:id/suggestions/confirm-high`）：服务端按 `confidence ≥ suggest_high` 批量 0→1，低置信与已处理行不动。主路径点击量从「N 条建议」降到「1 次 + 剩余低置信」。
2. **列表待确认计数**：`GET /teacher/growth/logs` 出参每条带 `pending_suggestions_count`（>0 才建议前端呈现），老师不打开详情就知道哪条待处理。
3. 批量点名面板补「全选照片」（同活动连续命名复用，见 D8 的面板）。
**不做**：自动确认（跳过老师）——信任模型不变，省力只省在「批量」维度，不省「老师知情」这一环。

**补记（2026-10-15 用户实测缺陷）**：批量面板原本不显示照片上**已有**的点名，老师「选 1 个孩子」后徽标从 2 变 3 → 不可预期（并集语义本身正确，问题在信息不可见）。修复：面板将已有孩子标为「已有」且不可取消、底部按钮预告「确定（共 N 人）」；同时修复**批量仅选 1 张时误走「替换」分支**（会清掉已有名单）的语义缺陷——入口决定语义（批量=追加 / 单张=编辑完整名单），不再用 targets 数量推断。

## Risks / Trade-offs

- **儿童脸识别质量不达预期** → 初测已完成（`docs/face-quality-report.md`，样本不完整、结论待真实数据复审）；**真实场景（活动合影/标注数据）充分验证后**校准 `suggest_high/suggest_low`；即使质量一般，人工点名路径不受影响（识别只是加速器），最坏情形退化为候选排序 + 全人工确认（阈值配置化，不改代码）
- **合规前置未完成就启用底库** → **上线门槛**：底库采集（学生人脸照片）在家长授权流程（独立变更）完成前 MUST NOT 对真实园所开启；本变更先以 `[face].enabled` 白名单 + mock 落地，真实底库采集等待授权变更
- **腾讯云 SDK 引入重量级依赖** → `tencentcloud-sdk-go` 只引 `iai` 子包；mock 实现不依赖它（构建标签/file 拆分），CI 可无 SDK 构建
- **DB 轮询在多实例部署下任务重复认领** → 认领用 `UPDATE ... SET status='processing', worker_id=? WHERE id=? AND status='pending'` 的原子条件更新（CAS）；当前单实例部署下天然安全，多实例时该模式仍然成立
- **阈值是成人脸调的** → 见第一条；阈值全部配置化，校准不改代码
- **建议确认端点带来的状态竞争**（老师确认与识别回写并发） → 确认只允许 `0→1/0→2`；识别回写只允许 `NULL→0`（`ON DUPLICATE KEY UPDATE` 时若已是 1/2 不覆盖）

### D11：人脸数分型与「全班（当日到场）」（2026-10-16 第二次对抗性审查后补）

**审查发现（30 人班 / 29 人在园 / 一张合影）**：
1. 腾讯云 `MaxFaceNum` 上限 **10**（我们已打到顶）——29 人合影最多出 10 个候选，**即使识别率 100%，逐人路线在容量上就是死的**；19 个家长在「只看我的孩子」里看不到合影。
2. 成本不对称：**漏标**（家长看不到孩子的照片）远贵于**误标**（看到孩子不在的大合影）→ 设计应向误标倾斜。
3. `SearchFacesReturnsByGroupResponse.FaceNum`（检测到的人脸数）我们从未使用——它免费给出照片分型。
4. **跨班建议可写入甚至可确认**：队列全园搜索、写建议无班级过滤，确认端点也不校验学生范围——真实 300 人库下会产生 B 班孩子出现在 A 班照片建议里的错误。

**决定**：
1. **人脸数分型**（`Search` 返回 `FaceNum`）：`FaceNum=1` 单人照（AI 最强场景，高置信预勾）/ `2~5` 小组照（建议+确认）/ **`≥ group_photo_min_faces`（默认 6）判为大合影 → 丢弃候选、不写逐人建议**，只把 `face_count` 落任务行供 UI 呈现。仍调 1 次 API（成本不变，白赚分型）。
2. **「全班（当日到场）」一键**：到场 = 本班在读 ∧ 无「明确不在」信号（已批准请假 / 考勤标记缺勤请假）；**无考勤数据时保守全员在册**（宁误标勿漏标）。落库仍是正常 `student_ids`（快照语义天然正确，事后请假不影响已发照片）。入口两处：详情页大合影 CTA（立即生效端点）+ 编辑页面板「全班」按钮（预勾可增减）。
3. **建议写入按记录范围过滤**（队列内复用 D9 口径：全班→本班在读；个体→记录关联学生）。
4. 大合影不再跑到「确认 10 条建议」的伪工作；单人/小组照路径不变。
5. 配置：`[face].group_photo_min_faces`；`FaceMatchThreshold = suggest_low`（云端先砍一道噪声）。交付侧产出《老师拍照与点名规范》（单人特写优先 / 大合影用全班 / 多人背景单人照手动点名）。

**不做（独立后继变更）**：**班级组搜索**——`CopyPerson` 把学生复制进 `kg{id}_cls{cid}` 组、搜索按班限定（候选从 300 人竞争缩到 30 人）。涉及升班/转班的底库生命周期同步，单独走一个 change。

## Open Questions

- **腾讯云 QPS 默认档与购买规格**：免费额度 1 万次/月之外，QPS 档位按实际峰值再定（实施第 1 段验证时确认）
- **底库照片规格**：`CreateFace` 的最小尺寸/清晰度要求与现有上传缩略图策略的匹配（实施时用真实照片验证）
- **学生毕业/转出时的底库注销时机**：与学籍状态流转（`status=2毕业/3退学`）的联动属运营策略，可在实施后按实际需要补
